# Project Status

## Architecture

```text
CustomTkinter desktop GUI (app/gui.py + app/ui_*.py)
        |  llama-cpp-python calls, run on a background thread
        v
LocalStoryEngine (app/engine.py)
        |
        v
llama_cpp.Llama over a user-supplied GGUF model (models/*.gguf)
```

`app/gui.py::StoryForgeApp` is the only entry point into the application logic; there is no CLI and no network service. It owns a single `Project` (`app/project.py`) — plot, characters, setting, and up to `MAX_CHAPTERS` `Chapter` objects (title, outline, content, summary) — and a single `LocalStoryEngine` (`app/engine.py`), which wraps exactly one `llama_cpp.Llama` instance. All generation (outline, chapter prose, chapter summary) runs on a background `threading.Thread` so the UI stays responsive during a run that can take from a few seconds (an outline) to tens of minutes (a full chapter on CPU); `self.after(0, ...)` is used throughout to marshal results back onto the Tk main thread.

`app/prompts.py` builds every prompt sent to the model (outline, chapter system prompt, section continuation, summary, refine, expand, selection rewrite) as a `ChatPrompt(system, user, prefill, raw)` and does the context-budget trimming (word-count based, not token based). Chapter prompts put the stable story bible and task first and the step-specific blocks (lorebook matches, remaining length, progress hints, the Author's Note last) after a `STEP-SPECIFIC CONTEXT` marker, so llama.cpp can reuse the KV prefix from section to section (`LlamaRAMCache` per loaded model). `app/chat_format.py` renders a `ChatPrompt` with the GGUF's Jinja chat template, a detected or chosen preset (Llama 3 / ChatML / Mistral / Alpaca) or raw completion; `app/sampling.py` holds the per-task samplers and seed. `app/engine.py` adds token-aware overflow handling on top of that: it counts real tokens with the loaded model's own tokenizer when available, and retries a prompt at progressively smaller context budgets (`CONTEXT_BUDGET_LEVELS`) before raising `ContextOverflowError`. A chapter is generated in `SECTION_TARGET_WORDS`-sized sections (default ~900 words) rather than in one call, both because local models degrade in coherence over very long single generations and because most consumer hardware can't hold a 10,000-word generation in one context window comfortably.

`app/repetition.py` is a separate, optional post-processing step: it flags and can replace overused words using NLTK's stopwords/WordNet corpora, falling back to a small built-in stopword list and no synonym substitution if NLTK's data isn't available (offline-first by design — see `docs/workflows/repetition-reduction/workflow.md`). `app/export.py` turns a finished `Project` into a `.docx` (via `python-docx`: title page, a page break per chapter, `*italic*`/`**bold**` as real runs), a hand-built EPUB 3, Markdown or plain `.txt`, all written atomically.

The project file is `.storyforge.json`, `format_version` 2 (`app/project.py::FORMAT_VERSION`; version-1 files are migrated on load by `migrate()`, a newer version loads with unknown fields ignored). It holds plot/characters/setting, title/author, the lorebook, sampling, the Author's Note, the export heading style, `history_limit` (default 20, 1-100; set with "Versiones guardadas por capítulo" on the Plot tab), the model path (relative to `models/` when possible) and the chapters (title, outline, purpose, content, summary + its source hash, history with source and timestamp). The app version is `app/__init__.py::__version__` (0.4.0).

`StoryForgeApp` itself (`app/gui.py`) keeps only what belongs to the whole window: preferences, unexpected-error reporting, the engine busy lock (`_set_engine_busy()`), dirty tracking, autosave, open/save/export and `run()`. Each tab and the menu are mixin classes in their own module that `StoryForgeApp` inherits from (`MenuMixin` in `app/ui_menu.py`, `ModelTabMixin` in `app/ui_model_tab.py`, `StoryTabsMixin` in `app/ui_story_tabs.py`, `LorebookTabMixin` in `app/ui_lorebook_tab.py`, `OutlineTabMixin` in `app/ui_outline_tab.py`, `ChaptersTabMixin` in `app/ui_chapters_tab.py`); `ChapterPanel` and `VersionHistoryDialog` live in `app/ui_chapter_editor.py` and the shared constants/helpers/`LimitedTextBox` in `app/ui_common.py`. Every user-visible UI text comes from `app/strings_es.py` (imported as `S`; texts with `{fields}` are used with `S.NAME.format(...)`), and `tests/test_strings_es.py` fails if a UI module grows an inline user-facing literal or references a missing text.

A single `Llama` instance is not safe for concurrent inference calls. `StoryForgeApp.busy` (set/read through `_set_engine_busy()`) is the app-wide mutual-exclusion flag that prevents two generations (or a generation and a model load, or a generation and a project switch / chapter add-remove) from running at once — see `docs/workflows/reliability/workflow.md`.

## Release

```text
StoryForge-App/StoryForge.exe                          -- build.bat (onedir; models/ kept across builds)
dist/installer/StoryForge-<version>-<variant>-setup.exe -- build.bat, only when Inno Setup 6 is installed
StoryForge-<version>-<cpu|cuda13>.zip                  -- CI artifact (and GitHub Release for a v<version> tag)
StoryForge-<version>-<variant>-setup.exe               -- GitHub Release for a v<version> tag (CI compiles the installer)
```

Built with `build.bat [cpu]` (default variant `cuda13`; recreates `.build-venv` from `requirements-build.txt` + the prebuilt llama-cpp-python 0.3.35 wheel (+ `requirements-cuda.txt` for cuda13), downloads the NLTK data, runs the tests with coverage, runs `pyinstaller --noconfirm --clean storyforge.spec`, which produces `dist/StoryForge/`, compiles the installer if Inno Setup 6 is found, then mirrors the build into `StoryForge-App/` — a fixed, easy-to-find location, since `dist/` is PyInstaller's own working directory and gets wiped/regenerated by `--clean` on every build), or automatically by `.github/workflows/build-exe.yml` on every push to `master`, on a `v*` tag and on demand (Python 3.12 on `windows-latest`: ruff, a Tcl/Tk warm-up, `pytest --timeout=300` with coverage uploaded as `coverage-<variant>`, PyInstaller, and `StoryForge-<version>-<variant>.zip` uploaded as an artifact; a tag that matches `__version__` also builds each variant's installer and publishes the zips and installers as a GitHub Release — see `docs/workflows/desktop-build/workflow.md`). The installer (`installer/StoryForge.iss`) is per-user (no admin, `%LOCALAPPDATA%\Programs\StoryForge`, Spanish wizard, optional desktop shortcut), installs `models\README.txt` but never removes models the user copied there, and clears `_internal\` on an upgrade. The app icon (`assets/icon.ico`, 16-256 px with simplified art at 16-32 px, and `assets/icon.png`, 512 px: an open book with a gold quill nib and sparks on a forge-lit indigo tile) is the exe icon, the window icon (`gui.window_icon_path()`, bundled by the spec) and the installer's. Both `dist/` and `StoryForge-App/` are gitignored build output, not part of the repo. `storyforge.spec` bundles `customtkinter`, `llama_cpp`, and `docx` via `collect_all()`, with an explicit `excludes` list (see "Recently Fixed") keeping out several heavy dependencies this app never uses. Model files are never bundled (several GB, not part of this repository, see `.gitignore`): `build.bat` creates `StoryForge-App/models/` holding only `models/README.txt`, and keeps that folder (with whatever `.gguf` the user put there) across rebuilds. NLTK's `stopwords`/`wordnet` are downloaded explicitly by `build.bat`/CI into `nltk_data/` and bundled as `_internal/nltk_data/` (about 11 MB; `omw-1.4`, 26 MB of non-English WordNets the app never reads, is no longer included; found at runtime through PyInstaller's nltk runtime hook), so every build works offline for "Reducir repeticion". `nltk_data/` at the project root stays gitignored.

Must be built on Windows — no cross-compiled `.exe` is produced from any other platform.

**Code signing:** with `CODESIGN_THUMBPRINT` set (the SHA-1 thumbprint of a code-signing certificate in the Windows store), `build.bat` checks for signtool before the build, signs `StoryForge.exe`, and passes Inno Setup a `codesign` tool so the installer and its uninstaller are signed too (`#ifdef Sign` in `installer/StoryForge.iss`), timestamped by `CODESIGN_TIMESTAMP_URL` (default DigiCert). CI doesn't sign.

Measured with `build.bat` on 2026-10-01 (Python 3.14 `.build-venv`, llama-cpp-python 0.3.35): the `cpu` variant is 116 MB and the `cuda13` variant 756 MB (`StoryForge-App/` excluding `models/`; ~640 MB of that is `cublasLt64_13.dll` 471 MB, `ggml-cuda.dll` 112 MB and `cublas64_13.dll` 52 MB in `_internal/llama_cpp/lib`, with no duplicate `_internal/nvidia/` copy). Both built in ~2 minutes, launched, and showed "StoryForge Local 0.4.0" in the title bar; the exe's version resource reads 0.4.0 (0.4.0.0); the bundled `llama.dll` reports `llama_supports_gpu_offload() == True` and loads cuBLAS from the bundle on an RTX 5080. See "Recently Fixed" below for what it looked like before the packaging fix, and `docs/workflows/desktop-build/workflow.md` for the full breakdown.

## Known Limitations

See the README's "Limitaciones reales que debes conocer" section for the user-facing version. Code-level ones:

- **Nothing since the P1 round has been run against a real GGUF.** Chat templates, sampling parameters (`min_p`, `seed`, presence/frequency penalties), `flash_attn`/`n_batch`/`type_k`/`type_v` and the tokens/s numbers are exercised with fakes only; run `tests/test_real_model.py` with a small model, and check output quality and VRAM use by hand.
- **The GUI was not opened in a real window.** Layout, the diff preview, the find bar highlight, the right-click selection menu, focus mode, the status bar and the light theme were only built headlessly; check them visually. `apply_editor_preferences()` touches CustomTkinter's private `_textbox` for line spacing.
- **The GUI split is by file, not by encapsulation.** The tab mixins share one `StoryForgeApp` instance and call each other's methods and attributes through `self` (for example the chapters tab reads `self.busy` and the lorebook's match ids); the modules make the code navigable but are not independent components. Moved code keeps logging under the `app.gui` logger name.
- **Backend texts live in `app/strings_es.py` too, but only the ones that reach the user.** Errors raised and load warnings in `app/engine.py`, `app/project.py`, `app/gguf.py`, `app/export.py` and `app/prompts.py`, and `LoreMatch.reason_es()`, use `S.*` texts (`tests/test_strings_es.py::test_backend_messages_come_from_strings_es`; `project.py` imports `strings_es` after the two lists `strings_es` itself imports from it). Log messages and the English prompt text stay where they are. The UI modules' inline-text check is a heuristic (letters plus a space, an accent or a leading capital), so a lone lowercase word added inline would slip through.
- **Retry ("Reintentar") repeats the whole last Generar/Continuar run**, not just its last section. Its alternatives are saved with the project (`Chapter.alternatives`/`alt_index`, the 10 newest, kept only while the shown one is still the chapter's text), but Retry itself needs the last run's starting point, which isn't saved: after reopening, < > still cycles the alternatives and Retry starts a new set.
- **VRAM estimate is approximate** (file size + KV-cache formula + a fixed 700 MB overhead) and needs `nvidia-smi`; without it the app cannot suggest `n_gpu_layers`.
- **`build.bat`'s signing step hasn't run end to end.** The installer itself was compiled and checked with a silent install/uninstall, and the same codesign wiring signed Photo Studio's and the media player's installers with a self-signed test certificate on 2026-10-07, but that environment couldn't execute `.bat` files: run `build.bat cpu` with `CODESIGN_THUMBPRINT` set once. Without a trusted certificate SmartScreen still warns.
- **The tag-triggered release job has never run** (no `v*` tag pushed; `v0.4.0` waits until GitHub Actions artifact uploads work again — the account's free monthly artifact storage ran out on 2026-10-07 and resets on 1 November). The `cpu`/`cuda13` matrix (ruff, tests with coverage, PyInstaller, version-named zips) runs on every push to `master`; until the quota resets its upload steps fail. CI doesn't launch the built `.exe`.
- **The last verified local `.exe` builds (2026-10-01, see "Release") predate the final icon, the Tab order and the prompt-layout change**, and no `StoryForge-App\` build is currently present: run `build.bat` and launch it before relying on the current code as an `.exe` (CI builds the zips but doesn't launch them).
