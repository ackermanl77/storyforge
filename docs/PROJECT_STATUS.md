# Project Status

## Architecture

```text
CustomTkinter desktop GUI (app/gui.py)
        |  llama-cpp-python calls, run on a background thread
        v
LocalStoryEngine (app/engine.py)
        |
        v
llama_cpp.Llama over a user-supplied GGUF model (models/*.gguf)
```

`app/gui.py::StoryForgeApp` is the only entry point into the application logic; there is no CLI and no network service. It owns a single `Project` (`app/project.py`) — plot, characters, setting, and up to `MAX_CHAPTERS` `Chapter` objects (title, outline, content, summary) — and a single `LocalStoryEngine` (`app/engine.py`), which wraps exactly one `llama_cpp.Llama` instance. All generation (outline, chapter prose, chapter summary) runs on a background `threading.Thread` so the UI stays responsive during a run that can take from a few seconds (an outline) to tens of minutes (a full chapter on CPU); `self.after(0, ...)` is used throughout to marshal results back onto the Tk main thread.

`app/prompts.py` builds every prompt sent to the model (outline, chapter system prompt, section continuation) and does the context-budget trimming (word-count based, not token based). `app/engine.py` adds token-aware overflow handling on top of that: it counts real tokens with the loaded model's own tokenizer when available, and retries a prompt at progressively smaller context budgets (`CONTEXT_BUDGET_LEVELS`) before raising `ContextOverflowError`. A chapter is generated in `SECTION_TARGET_WORDS`-sized sections (default ~900 words) rather than in one call, both because local models degrade in coherence over very long single generations and because most consumer hardware can't hold a 10,000-word generation in one context window comfortably.

`app/repetition.py` is a separate, optional post-processing step: it flags and can replace overused words using NLTK's stopwords/WordNet corpora, falling back to a small built-in stopword list and no synonym substitution if NLTK's data isn't available (offline-first by design — see `docs/workflows/repetition-reduction/workflow.md`). `app/export.py` turns a finished `Project` into a `.docx` (via `python-docx`, converting `*italic*` markers into real italic runs) or a plain `.txt`.

A single `Llama` instance is not safe for concurrent inference calls. `StoryForgeApp.busy` (set/read through `_set_engine_busy()`) is the app-wide mutual-exclusion flag that prevents two generations (or a generation and a model load, or a generation and a project switch / chapter add-remove) from running at once — see `docs/workflows/reliability/workflow.md`.

## Release

```text
StoryForge-App/StoryForge.exe
```

Built with `build.bat` (installs dependencies, runs `pyinstaller --noconfirm --clean storyforge.spec`, which produces `dist/StoryForge/`, then mirrors that into `StoryForge-App/` — a fixed, easy-to-find location, since `dist/` is PyInstaller's own working directory and gets wiped/regenerated by `--clean` on every build), or automatically by `.github/workflows/build-exe.yml` on every push to `master`/`test-story` (downloadable as a build artifact from the Actions run, named after the commit rather than placed in a fixed local path — see `docs/workflows/desktop-build/workflow.md`). Both `dist/` and `StoryForge-App/` are gitignored build output, not part of the repo. `storyforge.spec` bundles `customtkinter`, `llama_cpp`, and `docx` via `collect_all()`, with an explicit `excludes` list (see "Recently Fixed") keeping out several heavy dependencies this app never uses. The `models/` folder (with the user's own `.gguf` file inside) has to be copied next to the built `.exe` manually — it is never bundled, since model files are several GB and are not part of this repository (see `.gitignore`). NLTK's `stopwords`/`wordnet` corpora are handled differently: if the machine doing the build already has them cached in a standard NLTK search path (e.g. `%APPDATA%\nltk_data`), PyInstaller's `nltk` hook bundles that data automatically (observed: +11 MB, `_internal/nltk_data/`), so that particular build's `.exe` works offline for "Reducir repeticion" immediately. A build done on a machine with no cached NLTK data yet will **not** have it bundled and falls back to the one-time-download behavior described in `docs/workflows/repetition-reduction/workflow.md`. Either way, `nltk_data/` at the project root (not the bundled one) stays gitignored.

Must be built on Windows — no cross-compiled `.exe` is produced from any other platform.

A build with the current spec is ~137 MB. See "Recently Fixed" below for what it looked like before the packaging fix, and `docs/workflows/desktop-build/workflow.md` for the full breakdown.

## Verification

```powershell
python -m unittest discover -s tests -v
```

138 tests, no `llama-cpp-python` or real model required (`tests/test_engine.py` and `tests/test_outline.py` inject a `FakeLlama`/`StreamingFakeLlama` stand-in). Run this yourself before relying on a pass count — this line is not re-verified automatically as the code changes.

`app/gui.py` has narrow, targeted automated coverage in `tests/test_gui.py` (42 tests): the background-error-reporting paths for all five engine-calling actions (chapter generation, outline generation, model loading, field expansion, chapter refinement), plus the chapter-purpose dropdown's sync, the import-from-file flow, the version-history dialog's preview/restore, the Lorebook tab's add/edit/remove list-editor, and the token-streaming display's final-text-always-correct guarantee — all end to end against a real `StoryForgeApp`/`CTk` instance. It needs `customtkinter` and the ability to create a real Tk window, which the rest of the suite deliberately doesn't require — it `unittest.skipUnless`-guards itself (skips cleanly, doesn't fail) if either is unavailable, so `python -m unittest discover -s tests` still works without GUI dependencies installed; CI (`.github/workflows/build-exe.yml`) installs `requirements.txt` first, so it always runs there. Every test in this file clears `AUTOSAVE_PATH` in its own `setUp()` (see `_clear_autosave()`) before constructing `StoryForgeApp()`, since several actions autosave in a `finally` block regardless of success/failure -- without that, a leftover `autosave.json` from one test class gets silently recovered (or discarded) by the next one's `StoryForgeApp()` construction depending on how it mocks `askyesno()`, corrupting supposedly-fresh chapter indices. Everything else in `app/gui.py` — the busy-lock, exit confirmation, autosave, etc. — is still only verified with ad hoc smoke scripts that instantiate `StoryForgeApp` headlessly and drive it directly (see the "Recently Fixed" entries below for what each one checked), not committed tests.

## Known Limitations

See the README's "Limitaciones reales que debes conocer" section for the user-facing version of these (writing quality of small local models, limited context memory, CPU generation speed, model-specific content filters). Additional, code-level ones not covered there:

- **A project's `model_path` and engine settings aren't restored when you reopen it.** `Project.model_path` is saved (and updated on every successful `_load_model()`), but `_load_into_ui()`/`open_project()` never reads it back — reopening a project always shows "Ningun modelo cargado" in the Modelo tab regardless of what was loaded when it was saved, and the `n_ctx`/`n_gpu_layers`/`n_threads` fields always reset to their hardcoded defaults rather than whatever was used last. Not fixed; loading a model (with whatever settings you want) is a separate, manual step after opening a project.
- **Most of the GUI still has no test suite, `tests/test_gui.py`'s coverage aside.** Every fix under "Recently Fixed" below that touches `app/gui.py` — other than what `test_gui.py` covers (see "Verification" above) — was verified with a one-off script, not a committed regression test — a future change could silently reintroduce one of these bugs (e.g. the busy-lock gaps) with nothing failing in `python -m unittest discover -s tests`.
- **Autosave writes on the main thread.** `StoryForgeApp._autosave()` (see `docs/workflows/reliability/workflow.md`) does a blocking file write every 20 seconds while a generation is in progress. On a slow or network-mounted drive this could introduce a brief UI stutter; not something this project's scale has needed to address yet.

- **Three UI-review findings fixed: streaming flash-and-reset, no lorebook search/match feedback, and no chapter quick-jump.**
  - **Streaming no longer flashes back to the top.** `ChapterPanel._on_generate()`'s `progress` closure previously did a full `content_box.delete("1.0", "end")` + `insert("1.0", text)` with the WHOLE text generated so far on every throttled update (~every 150ms) -- if the user had scrolled down to read, the view snapped back to the top on the next tick. `progress_callback` always hands back the full cumulative text (not a delta), so it now tracks how much of that text is already shown (`stream_state["shown_text"]`) and appends only the new suffix via `content_box.insert("end", delta)`, auto-following with `content_box.see("end")` on every update (deliberate choice, documented in the closure, over tracking whether the user scrolled up manually). A non-monotonic update (text that isn't an extension of what's shown -- not expected, but not something to silently mis-render either) falls back to a full replace. The content box is now cleared once, synchronously, right before the worker thread starts, rather than on the first throttled update. The final/cancelled state still does one guaranteed-correct full delete+reinsert (`show_final`, matching the existing `TestChapterStreamingDisplay` coverage for "final text is always exactly right regardless of throttling").
  - **Lorebook tab: search box + "used last generation" badge.** A `CTkEntry` search box above the entry list (`StoryForgeApp.lore_search_entry`) filters visible entries by case-insensitive substring match against name or any keyword (`_lore_entry_matches_search()`, a standalone function for testability), re-rendering on every keystroke via the existing `_render_lore_entries()` teardown/rebuild pattern -- which now also syncs any in-progress edits in the currently-visible panels into the model before tearing them down, since a filter-triggered rerender happens far more often than the previous add/remove-only rerenders did. Separately, `StoryForgeApp._record_lore_matches(chapter_index)` recomputes `prompts.find_relevant_lore_entries()` against the same scan text `build_chapter_system_prompt()` used internally for that generation (chapter outline + previous-chapters summary) once a chapter finishes generating, storing matched entries' `id()`s in `self.last_lore_match_ids` and re-rendering the tab so each matched `LoreEntryPanel` shows a "usada en la ultima generacion" badge. Recomputed rather than threaded back from inside `generate_chapter()` (which doesn't return it) since it's cheap, pure string matching with no model call. Cleared on new/opened project (`_load_into_ui`) so a different project's lorebook doesn't show stale matches.
  - **Chapters tab: a persistent chapter-navigation sidebar.** `_render_chapters()` stacks every chapter's full panel (220px textbox + 6 buttons), all expanded, in one scrollable frame -- a long scroll at 10 chapters with no way to jump to a specific one. A second, narrow `CTkScrollableFrame` (`StoryForgeApp.chapter_sidebar`) now lists chapter number + title + a short content preview as clickable buttons; clicking one calls `_jump_to_chapter(index)`, which scrolls `chapters_scroll` to that panel via `chapters_scroll._parent_canvas.yview_moveto(fraction)` -- `CTkScrollableFrame` has no public "scroll to widget" API, but wraps a plain `tkinter.Canvas` at the (private but stable) `_parent_canvas` attribute, and the fraction is computed from the target panel's real Y position against the canvas's total scrollregion. Kept in sync with the main list by rendering from inside `_render_chapters()` itself rather than a separate call site. Chapters already visited aren't collapsed -- out of scope per the request, this is a navigation aid only.

- **Every error path in chapter generation, outline generation, and model loading silently failed instead of telling the user what went wrong.** Found by running `pyflakes` over `app/`, not by manual testing. Each of `ChapterPanel._on_generate()`, `StoryForgeApp._on_generate_outline()`, and `StoryForgeApp._load_model()` runs its work in a background thread and reports failure via `self.app.after(0, lambda: messagebox.showerror(APP_TITLE, f"...{exc}..."))` (or, for `_load_model`, into `model_status`'s text) inside `except ... as exc:`. Python deletes `exc` from scope automatically as soon as the `except` block ends; since `self.after(0, ...)` *defers* the lambda until the Tk event loop gets to it — always after the except block has already exited — referencing `exc` inside that lambda raised `NameError: cannot access free variable 'exc'...` instead of showing the real error. In the packaged, windowed (`console=False`) `.exe` this was completely silent: no dialog, no console output, nothing — a failed model load (e.g. a corrupted `.gguf`) or a context overflow would just leave the status text saying "Cargando..." forever with zero indication of what happened. All 7 occurrences across the 3 methods had this bug. **Fixed**: each `except` block now captures the message into a plain local variable first (not auto-deleted) and the lambda closes over that instead of `exc` directly. Added `tests/test_gui.py` (3 tests, one per method) that reproduce this exact failure mode end to end — confirmed each fails with the pre-fix code (temporarily reintroduced the bug in one location, watched the test catch it, reverted) — and now pass. - **The Esquema tab's "Numero de capitulos" field didn't resync.** Opening a different project (or starting a new one) left this field showing the previous project's chapter count instead of the newly loaded project's. **Fixed**: `_load_into_ui()` now resets it.
- **No autosave for long generations.** A single chapter can take 15-40 minutes on CPU; before this, nothing was written to disk until the user explicitly saved, so a crash or unexpected close lost all of that progress. **Fixed**: a separate `autosave/autosave.json` (distinct from the user's own save file) is written every 20 seconds while `self.busy` is true, and once more immediately when a generation finishes. On startup, if that file exists, the app offers to recover it. It is discarded automatically after an explicit save, or if the user declines to save when closing (an intentional "discard" shouldn't come back as an unwanted recovery prompt next launch). See `docs/workflows/reliability/workflow.md`.
- **Loading a model could briefly hold two full models in memory at once.** `LocalStoryEngine.load()` constructed the new `Llama` instance *before* releasing the reference to the old one, so switching models (or reloading the same one) meant both were fully resident in RAM/VRAM for the duration of the new model's construction — a real risk with multi-GB local models. **Fixed**: `load()` now calls `self.unload()` first.
- **The packaged `.exe` was several times larger than necessary, and slower to build than it needed to be.** `storyforge.spec`'s `collect_all("llama_cpp")` pulled in the whole package regardless of what this app actually imports (`app/engine.py` only ever does `from llama_cpp import Llama`) — in a build environment where `llama_cpp`'s optional `server` extra (an HTTP server) happened to be installed, PyInstaller's Analysis followed it into `uvicorn`/`fastapi`/`starlette`/`websockets`/`anyio`, and separately discovered `matplotlib` with a full `PySide6`/Qt backend (adding several minutes to the build just analyzing Qt) plus `pandas`/`pyarrow`/`scipy` pulled in by `nltk`'s own PyInstaller hook proactively including optional integrations (`app/repetition.py` only ever uses `nltk`'s stopwords/wordnet corpora, none of that). None of it was reachable from this app's own code (confirmed with `grep` across `app/`) — a build under those conditions produced a 425 MB `dist/StoryForge/`. **Fixed**: added an explicit `excludes` list to `storyforge.spec`'s `Analysis()` covering all of the above. Rebuilt and reverified the `.exe` still launches and runs correctly with the exclusions in place; the same build is now 137 MB (a ~3.1x reduction), dominated by `llama_cpp` (31 MB, the real compiled bindings), `numpy.libs` (21 MB), `PIL` (13 MB), and the incidentally-bundled `nltk_data` (11 MB, see "Release" above) — all things this app genuinely needs.
- **A chapter's outline had no size limit and wasn't covered by the context-budget shrinking mechanism.** Unlike plot/characters/setting/previous-chapters-summary, `chapter.outline` (free text, edited in the Esquema tab) was inserted into the chapter prompt at full length with no trimming and no validation — an unusually long outline could make even the smallest `CONTEXT_BUDGET_LEVELS` entry fail to fit, with a `ContextOverflowError` message that misleadingly implied everything had already been reduced to a minimum. **Fixed**: added `MAX_OUTLINE_WORDS_PER_CHAPTER` (800 words) to `validate_inputs()`, a `max_outline_words` entry in each `CONTEXT_BUDGET_LEVELS` level, trimming in `build_chapter_system_prompt()`, and a live word counter in `OutlinePanel` matching the one Plot/Personajes/Setting already had.
- **Outline-first workflow, and a stale-data bug found while building it** (carried over from the README's own changelog, kept here as the earliest recorded history for this project). Added the "Esquema" tab: generate a full chapter-by-chapter beat sheet up front from plot/characters/setting, edit it, then have chapter generation follow it (`build_chapter_system_prompt`'s `THIS CHAPTER'S OUTLINE` block, plus a compact all-chapter-titles overview for whole-story awareness). While building it, found that generating a chapter or the outline only synced the plot/characters/setting/outline fields from the UI into the `Project` on save/export, not on generate — so generating without saving first could silently use stale or empty data. Fixed by having both generate actions call `_sync_all()` first.
